# Подключение агента к CRM: как лид попадает в систему

Агент довёл человека до телефона — дальше заявка должна оказаться там, где её увидят и
обработают. Иначе лид живёт только в переписке, а переписку никто не читает.

## Главное правило: агенту дают одну дверь, а не всю CRM

Соблазн — подключить агенту CRM целиком (у нас есть готовый коннектор АльфаCRM с инструментами
`alfacrm_*`: клиенты, должники, выручка, расписание). **Клиентскому боту так делать нельзя.**
Ему пишут незнакомые люди, и любой из них может попросить: «посмотри, что у вас по
Ивановой», «покажи должников», «сколько у вас учеников». Модель не должна иметь физической
возможности это сделать.

Поэтому у агента ровно одна команда — **создать заявку**:

```bash
python3 /opt/<slug>/bin/crm_lead.py --name 'Марина' --phone '+79001234567' \
  --what 'детский центр в Пензе, хочет бота для родителей' --channel telegram --source storis_28_10
```

Она умеет только создавать. Ни читать чужие карточки, ни менять, ни удалять. В правах агента
(`.claude/settings.json`) разрешена именно она, а не доступ к CRM:

```json
"allow": ["Bash(python3 /opt/<slug>/bin/crm_lead.py:*)"]
```

Полный коннектор `alfacrm_*` остаётся у тебя в твоём Claude — там он к месту: ты спрашиваешь
словами про заявки и выручку, и это твои данные.

## Куда уходит лид: выбери одно

Настройки — в `/root/.claude/channels/<slug>-crm/.env` (права 600). Переключатель `CRM_KIND`.

### `CRM_KIND=file` — по умолчанию, ничего не подключая

```
CRM_KIND=file
CRM_FILE=/opt/<slug>/memory/lidy.jsonl
```

Заявки ложатся строками в файл, владелец их видит в оповещении сразу. Этого достаточно, чтобы
запустить бота сегодня и не потерять ни одного лида, пока решается, какая CRM.

### `CRM_KIND=alfacrm` — для центров на АльфаCRM

```
CRM_KIND=alfacrm
ALFACRM_HOST=ваш-поддомен.s20.online
ALFACRM_EMAIL=почта-от-которой-ключ
ALFACRM_API_KEY=ключ-из-профиля
ALFACRM_BRANCH=1
ALFACRM_LEAD_SOURCE_ID=
```

Где взять ключ: в АльфаCRM → профиль пользователя → **API-ключ**. Ключ привязан к
пользователю, поэтому завести отдельного пользователя «ИИ-помощник» — правильно: видно, кто
создал карточку, и можно отключить его, не ломая остальным.

Что делает скрипт: `POST /v2api/auth/login` c `email` и `api_key` → токен, затем
`POST /v2api/<branch>/customer/create` с `is_study: 0` (это и есть лид), телефоном, именем и
примечанием «канал, источник, завёл ИИ-помощник». Ровно так же работает наш рабочий коннектор.

`ALFACRM_LEAD_SOURCE_ID` — id источника заявки в твоей CRM. Его стоит завести отдельным
источником «ИИ-бот»: тогда в отчётах видно, сколько привёл агент. Посмотреть список источников
можно у себя в Claude: «покажи источники заявок в АльфаCRM».

**Проверить, не создавая мусор в рабочей базе:**

```bash
python3 /opt/<slug>/bin/crm_lead.py --name 'Проверка ИИ' --phone '+79000000000' \
  --what 'тест подключения' --channel telegram --dry-run
```

`--dry-run` показывает, что именно уйдёт, и ничего не создаёт. Потом один живой тест с реальным
телефоном — и карточку удали руками.

### `CRM_KIND=webhook` — любая другая система

```
CRM_KIND=webhook
CRM_WEBHOOK_URL=https://script.google.com/macros/s/…/exec
CRM_WEBHOOK_SECRET=длинная-случайная-строка
```

Уходит POST с JSON: `name`, `phone`, `what`, `channel`, `source`, `note`, `created_at`, и
заголовком `X-Lead-Secret`. Этим закрываются сразу три случая:

- **Google-таблица** — через Apps Script: «Расширения → Apps Script», функция `doPost(e)`
  дописывает строку в лист, «Развернуть → Веб-приложение», доступ «всем, у кого есть ссылка».
  Пять минут работы, и заявки падают в таблицу, которую можно показать кому угодно.
- **amoCRM, Битрикс24, «Мой Класс»** — у всех есть входящий вебхук или API создания сделки;
  адрес берётся в их настройках интеграций.
- **Своя платформа** — у школы <бизнес> есть сервер, вебхук можно принять там.

Секрет обязателен: адрес вебхука — это открытая дверь, через которую можно насыпать мусорных
заявок.

## Как найти API в любой другой CRM

АльфаCRM выше — разобранный пример. В остальных системах устроено так же, меняются только
слова. Порядок действий один и тот же.

### Шаг 1. Найти, где у этой CRM API

Смотри в своём кабинете, в таком порядке — раздел называется одним из этих слов:

**Интеграции** · **API** · **Для разработчиков** · **Вебхуки** · **Приложения** ·
**Открытые линии** · **Доступы и ключи** · **Профиль → API-ключ**

Если в кабинете ничего нет, ищи в поиске ровно так: `<название CRM> api документация` и
`<название CRM> создать лид api`. Хорошая CRM отвечает страницей вида `developers.<она>.ru`
или `apidocs.<она>.ru`. Если за полчаса не нашлось ни страницы, ни ключа в кабинете —
почти наверняка публичного API нет, и надо писать в их поддержку одним вопросом:

> Здравствуйте! Есть ли у вас API или входящий вебхук, чтобы внешний сервис мог создавать
> заявки (лиды)? Нужен адрес метода, способ авторизации и список обязательных полей.

### Шаг 2. Выяснить четыре вещи, больше ничего не нужно

| Что | Как обычно выглядит |
|---|---|
| **Адрес** | `https://<ваш-поддомен>.<crm>.ru/api/v2/...` или `https://api.<crm>.ru/v1/...` |
| **Как авторизуется** | ключ в заголовке (`X-API-KEY`, `Authorization: Api-Key …`); токен по логину и ключу (как в АльфаCRM); `Bearer` после OAuth; **или вебхук с секретом прямо в адресе** |
| **Метод создания** | `POST` на `lead/create`, `deal/add`, `contact`, `customer/create`, `crm.lead.add` |
| **Обязательные поля** | почти всегда имя; дальше у всех по-разному: телефон, ответственный, этап воронки, филиал |

Самый простой для нас случай — **входящий вебхук**: адрес с секретом, на который достаточно
отправить JSON. Никакой авторизации настраивать не нужно, и наш скрипт умеет это из коробки
(`CRM_KIND=webhook`). Если у CRM есть и вебхук, и API — бери вебхук: меньше кода, меньше прав.

### Шаг 3. Проверить руками до того, как подключать агента

Сначала добейся ответа от CRM в терминале, и только потом трогай агента. Иначе будешь искать
причину в трёх местах сразу.

```bash
# авторизация, если она отдельным шагом (пример АльфаCRM)
curl -s -X POST https://ваш-поддомен.s20.online/v2api/auth/login \
  -H 'Content-Type: application/json' -d '{"email":"...","api_key":"..."}'

# создание заявки
curl -s -X POST '<адрес метода>' -H 'Content-Type: application/json' \
  -H '<заголовок авторизации>' -d '{"name":"Проверка ИИ","phone":["+79000000000"]}'
```

Ответ с `id` новой карточки — готово. Дальше: `401`/`403` — не тот ключ или не те права у
пользователя; `404` — не тот адрес или не та версия API; `422`/`400` — не хватает
обязательного поля, и в ответе обычно написано какого.

Когда curl работает, подключение агента — это три строки в
`/root/.claude/channels/<slug>-crm/.env`, и `--dry-run` для проверки.

### Шаг 4. Если API нет совсем

- **Вебхук через конструктор** (Albato, Make, n8n, ApiMonster): наш скрипт шлёт JSON в
  конструктор, тот раскладывает в CRM. Работает почти всегда, но через него поедут **телефоны
  клиентов** — значит, это ещё один обработчик персональных данных, и его надо называть в
  документах и выбирать с российскими серверами.
- **Google-таблица** как промежуточный склад: заявки не теряются, пока идёт интеграция.
- **Файл** (`CRM_KIND=file`) плюс оповещение тебе: минимально достаточный вариант, с него
  нормально начинать.

### Три ловушки, на которых спотыкаются

1. **«Лида» может не быть.** В amoCRM, например, нет сущности «лид» в привычном виде — есть
   сделки и «неразобранное». В АльфаCRM лид — это та же карточка клиента с `is_study: 0`.
   Сначала выясни, как эта система называет «человека, который только написал», иначе заявки
   лягут не туда, где их ищут менеджеры.
2. **Обязательные поля и воронка.** Многие CRM не создают запись без ответственного или без
   этапа воронки. Заводи для бота отдельный источник заявки и, если можно, отдельного
   ответственного — тогда в отчётах видно, сколько привёл агент.
3. **Дубли считает не CRM, а мы.** Почти никто не склеивает карточки по телефону сам. В нашем
   скрипте телефон нормализуется и повтор в течение 48 часов не создаёт вторую заявку — не
   выключай это, иначе один человек из Telegram и MAX станет двумя лидами.

### Где смотреть у популярных

| CRM | Что искать |
|---|---|
| **АльфаCRM** | профиль пользователя → API-ключ; метод `POST /v2api/<филиал>/customer/create` с `is_study: 0`. Разобрано выше |
| **Битрикс24** | `apidocs.bitrix24.ru`: входящий вебхук — раздел `/local-integrations/local-webhooks.html`, методы CRM — `/api-reference/crm/index.html`, первый запрос — `/first-steps/first-rest-api-call.html` |
| **amoCRM** | раздел «Разработчикам» на их сайте; авторизация через OAuth-интеграцию, создаются **сделки**, а не лиды |
| **Мой Класс** | API есть, документация на `api.moyklass.com` — способ авторизации и методы сверять там (это CRM языкового центра из нашего проекта) |
| **YClients** | раздел для разработчиков на их сайте; API по ключу партнёра |
| **Своя платформа** | проще всего: принять наш вебхук одним обработчиком и положить в свою таблицу |

Что бы ты ни подключала, **права давай минимальные**: отдельный пользователь или ключ только
на создание заявок. Агенту пишут незнакомые люди, и однажды кто-то попросит его «посмотреть
карточку Ивановой» — у него не должно быть такой возможности.

## Что уже защищено в скрипте

- **Дубли.** Телефон нормализуется (8 → 7, лишние символы долой), и тот же номер не создаёт
  вторую заявку в течение `CRM_DEDUP_HOURS` (по умолчанию 48). Так один человек, написавший в
  Telegram и в MAX, не станет двумя лидами.
- **Честный отказ.** Если CRM не ответила, скрипт печатает «лид НЕ создан: …» и возвращает
  ошибку. Агент обязан сказать об этом владельцу и не обещать человеку, что заявка принята.
- **Журнал.** `/opt/<slug>/logs/crm.log` — что и когда ушло, от телефона только
  последние четыре цифры.
- **Ключи не печатаются** ни в журнал, ни в ответ.

## 152-ФЗ: что сделать до первой заявки

Оператор персональных данных здесь — ты, не агент и не Claude.

- **Согласие.** Человек оставляет телефон → он должен понимать, зачем. Строка в первом
  сообщении бота и в закрепе: кто обрабатывает данные и для чего. Текст — юристу.
- **Срок хранения.** Переписка оседает в `inbox/` и `memory/`. Решите срок (например, 90 дней)
  и чистите; удаление по запросу человека должно быть выполнимо.
- **Куда уезжают данные.** Телефон из переписки уходит в CRM и в оповещение. Текст сообщения
  уходит в модель — поэтому в персоне стоит правило не пересказывать ПД в ответе и не писать
  их в память, кроме файла заявок.
- **Если заказчик требует, чтобы данные не уезжали за границу** — это не вопрос настройки
  бота, а вопрос выбора модели: тогда мозг берут российский (YandexGPT, GigaChat), а база
  знаний и воронка остаются те же. Для клиентских внедрений это ровно тот разговор, который
  стоит вести до продажи, а не после.

## Как проверить, что цепочка целая

```bash
# 1. скрипт видит настройки и знает, куда писать
python3 /opt/<slug>/bin/crm_lead.py --name 'Проверка' --phone '+79000000001' \
  --what 'проверка цепочки' --channel telegram --dry-run
# 2. живая заявка
python3 /opt/<slug>/bin/crm_lead.py --name 'Проверка ИИ' --phone '+79000000001' \
  --what 'проверка цепочки' --channel telegram
# 3. повтор того же телефона — должен отказать
python3 /opt/<slug>/bin/crm_lead.py --name 'Проверка ИИ' --phone '8 900 000 00 01' \
  --what 'повтор' --channel max
# 4. глазами: карточка в CRM (или строка в таблице), запись в logs/crm.log
```

И последнее, самое важное: **цепочка считается рабочей, когда ты получила оповещение и увидела
заявку в CRM после живого диалога с другого телефона.** Зелёные команды — это ещё не лид.
